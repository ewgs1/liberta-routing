# Liberta Routing: направление разработки

Дата аудита: 14.11.2026. Это решение о дальнейшей архитектуре; статус каждой части указан отдельно. Текущее покрытие и испытания остаются в COVERAGE.md и COMPATIBILITY.md. Начальный автоматический сбор кандидатов реализован и описан в DISCOVERY.md; сервисные IP-правила и приёмка на телефонах пока не выполнены.

## Назначение

Liberta Routing — собственная поддерживаемая база выбранных сервисов и генератор правил для подписок Liberta и внешних пользователей. Основной режим: весь публичный трафик через proxy, известные сервисы и подтверждённые зависимости напрямую. Российская зона и все зарегистрированные за РФ сети не становятся direct автоматически.

Рабочий профиль прежней системы сохранён как исторический совместимый вариант. Его имя и номер выпуска не определяют устройство новой базы. Данные обновляются отдельными ревизиями; версия программы и ревизия данных — разные величины.

## Что уже существует

- Собственный реестр с 173 доменными правилами, генерация Xray/sing-box/TXT, полный пример Remnawave и native-профили Happ.
- Проверка полного покрытия provenance, воспроизводимости форматов, изменений маршрутов и публичных файлов.
- Нативные проверки ядер, локальный стенд реальной маршрутизации Xray и отдельный стенд DNS.
- Тестовая ветка с изменениями в GitHub. Основная ветка и опубликованный канал пока содержат прежнюю базу.
- Начальный сбор кандидатов для семи сервисов: страницы, CSP, разрешённые JS/CSS, DNS/CNAME, опциональные CT и RIPEstat; без автоматического изменения правил.

Это инженерная основа. Приёмка приложений на телефонах и собственный проверенный набор сервисных IP пока отсутствуют. В provenance остаются записи pending-review.

## Единица данных — сервис

Следующий шаг — добавить слой описания сервисов поверх работающего реестра, сохранив действующий генератор до проверки миграции. Категория «банки» не заменяет описание конкретного банка.

Для сервиса нужны:

1. Идентификатор и имя, например tbank.
2. Основные домены, API, авторизация, изображения/видео и платёжные зависимости. Родительский суффикс применяется только при осознанном согласии направлять все его поддомены напрямую.
3. У каждого утверждения — источник, дата, способ наблюдения и предел достоверности. Ссылка в официальном документе, CSP страницы, DNS-ответ и успешный вход в приложение являются разными видами доказательства.
4. Необязательные сети: источник принадлежности, диапазон, ASN/держатель, дата проверки, исключительность или совместное использование. Пустой набор IP означает отсутствие подтверждения, а не отсутствие соединений по IP.
5. Сценарии приёмки с версиями клиента, ядра, ОС, приложения и ревизией набора.

Приоритетные сервисы для первой приёмки: Т-Банк, Госуслуги, VK, Яндекс, Ozon и Wildberries. Далее — остальные сервисы текущего реестра.

## Домены, DNS и сети

Защита от пропусков строится из нескольких механизмов:

- Проверенные доменные суффиксы и узкие исключения.
- DNS через контролируемое окружение клиента, распознавание HTTP/TLS/QUIC там, где протокол раскрывает имя.
- DNS-сопоставление/FakeDNS только в явно проверенном режиме клиента. Оно помогает восстановить имя после наблюдавшегося DNS-запроса, но не определяет произвольный заранее известный IP.
- Явные префиксы сервисов при подтверждённой принадлежности и приемлемой широте охвата.

Включение сети конкретного сервиса не превращает режим в direct для всей России. Однако ASN облака, оператора или CDN может обслуживать множество чужих сервисов. Один IP тоже может быть общим. Нельзя автоматически добавлять весь ASN по одному CNAME или расширять наблюдённый IP до /24.

RIPE/RDAP/BGP помогают проверить регистрацию и объявления сетей. Поле country не доказывает физическое расположение сервера, а принадлежность ASN не доказывает принадлежность каждого приложения в нём. Список зарегистрированных за РФ префиксов — самостоятельная широкая политика, не эквивалент выбранных сервисов.

Корень суффикса не обязан иметь A/AAAA-запись. Рабочий поддомен может существовать при неразрешающемся корне. Один DNS-сбой или HTTP 403/498 не является основанием удалить правило. Наблюдения формируют кандидатов на разбор; они не меняют маршруты сами.

## Доставка пользователю

Единый проверенный снимок данных порождает разные упаковки:

| Потребитель | Доставка |
| --- | --- |
| Remnawave / Happ с JSON-подпиской | Генерируемый клиентский Xray-шаблон; панель подставляет приватные параметры подключения |
| Happ с native-routing | Профиль, доставленный через поддерживаемый механизм подписки; собственные Geo URL возможны по документации |
| sing-box | source JSON и позднее бинарный SRS; remote rule-set обновляется средствами клиента |
| Другие пользователи | TXT и Xray JSON-фрагмент с документированным назначением |

Полный JSON в Happ получает маршруты из самого JSON; native-профиль не накладывает поверх него свои DirectSites. Параметры окружения туннеля и геофайлов обслуживаются клиентом отдельно. На точной версии это требуется испытать вместе с итоговым ответом подписки.

Xray сам не скачивает произвольный JSON-фрагмент как remote rule-set. Обновление файла на GitHub не обновляет автоматически вручную вставленный шаблон в панели. Для интеграции необходим явный импорт проверенной ревизии в шаблон или управляемая синхронизация с журналом и откатом.

Собственный geosite.dat имеет смысл как дополнительный формат: Happ документирует загрузку геофайлов. Это упаковка тех же данных, а не способ получить более полное покрытие. Её добавление не должно блокировать первый проверенный путь Remnawave → Happ iOS с inline-правилами.

## Обновления и публикация

Целевой цикл: сбор кандидатов → обзор источников и изменений → PR → проверка сборки/маршрутов → кандидат для устройств → публикация одобренной ревизии. Для рутинных наблюдений нужен календарный запуск; публикация новых маршрутов не должна зависеть только от успешного сетевого запроса.

Сохраняются блокировки массового расширения/удаления, контроль прямых исключений общих сетей, воспроизводимость, контрольные суммы и предыдущий рабочий снимок. Уменьшение списка после недоступности источника требует отдельного разбора. Ревизию, полученную телефоном, нужно уметь установить по фактам, а не по заголовку latest.

Домены и правила собираются независимо из первичных документов и собственных наблюдений. Чужие готовые подборки не импортируются под видом собственных; условия используемых источников проверяются до публикации данных. VPN-узлы, ключи, токены, исходные пользовательские журналы и внутренние точки диагностики остаются вне публичной части.

## Когда этап считается завершённым

1. Один и тот же реестр собирает все заявленные форматы; пропуск обязательной зависимости сервиса выявляется проверкой.
2. Для приоритетных сервисов просмотрены источники и отдельно записаны неизвестные зависимости и сети.
3. Реальный ответ тестовой подписки Remnawave импортируется в Happ iOS; зафиксированы версии и ревизия правил.
4. Выполнены холодный запуск и вход в банк, история, открытие СБП до подтверждения, документы Госуслуг, фото/видео/сообщения VK, поиск и корзина маркетплейсов, зарубежный сайт через proxy. Затем те же сценарии повторяются в мобильной сети.
5. Наблюдённые адресаты и фактические маршруты соответствуют ожидаемым. Успешное открытие экрана без сведений о маршруте не выдаётся за доказательство direct.
6. Проверены обновление на новую ревизию и возврат к предыдущей. Затем — Android и другие клиенты.

Это подтверждает поддержку проверенных версий и сценариев, но не всех будущих соединений приложения. Список маршрутов также не скрывает факт существования VPN-интерфейса и не является системой противодействия DPI самого VPN-транспорта.
