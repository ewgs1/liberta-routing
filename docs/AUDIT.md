# Технический аудит alpha

## Границы

Проверены присланные `registry/registry.json`, `scripts/build.mjs`, `scripts/compare-lists.mjs`, `_internal/service-canary.mjs`, Smart v5 и код новой отдельной alpha. Старый реестр содержит 13 классов, 111 уникальных доменов и 45 явных direct-записей. Сборка Smart v5 воспроизведена побайтово: [результат](LEGACY_REGRESSION.md).

Рабочий профиль не активировался и не менялся. Новый выборочный профиль тестируется отдельно; старый реестр и сырые диагностические материалы не публикуются. Compatibility-сборщик сохранён в `scripts/build.mjs`; новый генератор трёх форматов расположен в корневом `build.mjs`.

## Находки в исходниках

| Находка | Последствие | Исправление / решение |
| --- | --- | --- |
| Сборщик добавлял зарубежные сбои без домашнего baseline; пустой baseline также снимал проверку | Случайный timeout мог расширить direct | В compatibility-сборщике baseline обязателен, конкретный домен должен иметь `ok`/`redirect`; три регрессионных теста |
| В `registry.json` есть метаданные узлов | `.gitignore` для отчётов не защищает сам реестр | Исходный реестр сохранён только закрытым; новый публичный schema не допускает `nodes` |
| `compare-lists` считает все классы «нашим явным списком», включая `explicit: false` | Метрика покрытия не соответствует явному правилу сборки | Новое сравнение использует только реально одобренные маршруты |
| При раскрытии категорий `full` заменяет `domain` для одного хоста | Объединение правил ошибочно сужается | Дефект воспроизведён из чистых функций; внешние категории в alpha не используются |
| Покрытие внешнего суффиксного правила проверяется только по его корневому хосту | Точный `full` может ошибочно считаться покрытием всех поддоменов | В alpha точное совпадение едино во всех форматах, границы поддоменов проверены тестами |
| Canary допускает `--insecure`, считает 403/451 блокировкой, а 404 обычно `ok` | Результат может означать WAF/ошибку запроса/непроверенный TLS | Новый canary не отключает TLS и не объявляет HTTP-код доказательством цензуры |
| DNS для отчёта и HTTPS разрешаются отдельно; ограничение ответа не прекращает приём потока | Замер может относиться к другому адресу; длинный поток задерживает проверку | Закреплённый публичный адрес, HEAD без тела и общий предел времени |
| Отчёт хранит данные точки наблюдения и redirect; отдельные документы содержат инфраструктуру | Прямая публикация архива раскрыла бы закрытые данные | Архив не коммитится; отчёты, исходный реестр, архитектурный документ и старые профили исключены |
| Старый CI только пересобирает Xray и смотрит diff | Нет строгой схемы, тестов маршрутов, secret scan, native parser check | Добавлены отдельные jobs и release gate |

Исходный comparator, работающий с чужими подборками, не запускается и не публикует скачанные данные. Для задачи независимого реестра он заменён собственным diff эффективных маршрутов, а не импортом внешнего содержимого.

## Архитектура

`registry.json` → строгая проверка → детерминированные три экспорта → immutable-каталог версии с SHA256. Отдельные ветви: `compare-lists.mjs` для эффективного diff и canary только для наблюдений. Интеграция создаёт новый закрытый тестовый профиль, не изменяя исходный файл и не активируя его.

## Риски и принятые меры

| Риск | Мера в alpha | Оставшаяся проверка |
| --- | --- | --- |
| Обход VPN из-за слишком широкого российского списка | Только точные хосты; суффиксы нельзя одобрить; без country/geosite/geoip | Проверить назначение каждого нового хоста |
| Разная семантика JSON и TXT | Xray `full:`, sing-box `domain`, типизированный TXT; общие тестовые случаи | Проверить импорт в конкретных приложениях |
| Прямой выход по умолчанию при неправильном порядке outbounds | Xray имеет последний TCP/UDP-маршрут `proxy`; sing-box требует `route.final` | Проверить реальные теги и механизмы выбора узла в Remnawave |
| Удаление правил после единичного сбоя | Canary не пишет в реестр; источник и сеть проверяются отдельно | Наблюдения из целевых сетей |
| Публичная диагностика раскрывает инфраструктуру | Отчёты только в `.private/`; CI не загружает их | Ручной просмотр содержимого и доменных имён |
| DNS rebinding / SSRF в canary | Отказ при любом непубличном DNS-ответе, закреплённый адрес, TLS, без redirect | Реальный сетевой прогон и дополнительные IP-диапазоны при изменении стандартов |
| Зависание или шквал запросов | Ограничение времени DNS/HTTPS и параллельности; HEAD без чтения тела | IPv6-only и особенности сетей |
| Незаметное изменение выбора маршрута | Эффективный hash и diff, `route-lock.json` с датой/причиной, тесты, ручная публикация | Защита ветки и обязательный независимый review после настройки GitHub |
| Частично записанный релиз | Временный каталог и атомарное переименование, отказ от перезаписи | Клиент должен загружать версию целиком перед переключением |
| Подмена внешнего инструмента CI | Версии и SHA256 официальных архивов закреплены; извлекается один executable | Планово пересматривать версии и проверять новые digest |
| Чужие данные с лицензионными обязательствами | Нет импорта готовых баз; собственный выбор по первичным источникам | Не принимать непроверенные массовые импорты |
| Просроченный обзор источника | 90 дней; новая сборка останавливается, старый выпуск не изменяется | Создать новый выпуск после ручной проверки |

## Существенные ограничения

1. Восемь хостов не составляют полное покрытие Госуслуг и ФНС. Внешние API, авторизация и CDN могут продолжить идти через VPN. ESIA и неизвестные поддомены автоматически не включались.
2. Доменные правила сработают, только если ядро знает целевой домен. IP-only, настройки TUN/FakeIP, sniffing, ECH/QUIC и DNS требуют самостоятельной проверки. Добавлять широкие прямые IP-маршруты как автоматическое исправление нельзя.
3. Маршрутизация DNS — отдельный вопрос. Alpha не переписывает DNS, сертификаты или sniffing исходного профиля. Сохранение DNS в копии не доказывает отсутствие DNS-утечек и соответствие выбранному direct/VPN-маршруту.
4. Простой Base64-набор ссылок подключения не переносит произвольные правила Xray/sing-box. Нужны соответствующие шаблоны подписки и клиент, который применяет эти поля.
5. `route-lock.json` обнаруживает незапланированное расхождение, но человек, способный менять код и lock, может одобрить любое изменение. Это не подпись и не замена защите ветки, review и контрольной сумме из доверенного канала.
6. SHA256 manifest защищает целостность только при доверенной заранее полученной сумме. Сумма, скачанная вместе с подменённым файлом из одного недоверенного канала, не доказывает подлинность.
7. Публичный сканер ищет характерные значения и поля; он не гарантирует распознавание всех токенов, диагностических FQDN и персональных данных. Просмотр diff перед публикацией обязателен.
8. Публичные GitHub Actions показывают системные технические сведения о стандартном runner. Собственная диагностическая инфраструктура и приватные сборщики к этим workflow не подключаются.

## Следующий аудит исходной системы

Проверить реальные шаблоны подписок Remnawave, теги outbound, системные правила и DNS на конкретных клиентах. Сравнить старый и новый выбор на пользовательских сценариях; отдельно провести измерения в целевых сетях. Сохранённая побайтовая регрессия не заменяет этот этап. До завершения испытаний Smart v5 остаётся отдельным рабочим профилем.
