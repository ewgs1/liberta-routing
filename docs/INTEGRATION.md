# Подключение к Remnawave и клиентам

Правила одинаковы для ОС, но применяет их ядро конкретного клиента. JSON-файл не устанавливает системный VPN, не включает TUN и не создаёт подключение к серверу.

## Remnawave / Xray

Для рабочего Smart v5 используйте сохранённый шаблон. Он не меняется при сборке alpha.

Для испытания создайте второй шаблон `XRAY_JSON` и назначьте его отдельной тестовой группе через механизм Templates / External Squads / Routing Rules. Вставьте содержимое `smart.xray.json` как значение корневого поля `routing`. Это не список серверов и не весь шаблон. В итоговой подписке нужны outbounds с тегами `direct` и `proxy`; `proxy` должен вести на предоставленный пользователю узел. Не добавляйте настоящие подключения в этот репозиторий.

У присланного Smart v5 есть `remnawave.addVirtualHostAsOutbound: true`: панель должна подставить основной outbound `proxy`. Не предполагайте, что этот тег появится при запуске JSON вне Remnawave. Дополнительные хосты, selector и механизм инжекта требуют проверки фактической версии панели и прав тестового пользователя.

Проверьте полученную клиентом подписку: порядок правил, наличие `proxy`, использование именно нового шаблона и отсутствие чужих широких direct-правил, добавленных клиентом. Base64-подписка из ссылок подключения произвольный объект `routing` не передаёт.

Xray не умеет использовать произвольный удалённый JSON как `geosite`. Публикация файла даёт URL для сборщика/администратора, а не автоматическое подключение списка внутри Xray. Обновление Xray-подписки требует вставки новой проверенной версии в шаблон.

## sing-box

`smart.singbox.json` — source rule-set версии 1 с точными именами. Сохраните проверенный файл рядом с конфигурацией и добавьте к существующему объекту `route`:

```json
{
  "rule_set": [
    {
      "type": "local",
      "tag": "liberta-smart-alpha",
      "format": "source",
      "path": "smart.singbox.json"
    }
  ],
  "rules": [
    {
      "rule_set": ["liberta-smart-alpha"],
      "action": "route",
      "outbound": "direct"
    }
  ],
  "final": "proxy"
}
```

Пример показывает только часть `route`, без DNS и подключения. Существующие специальные правила должны быть разобраны до применения. `action: route` ориентирован на sing-box 1.11+. Проверка source-формата не равна поддержке произвольной версии всего шаблона.

Remote rule-set допустим, когда приложение это поддерживает: `type: remote`, `format: source`, фиксированный URL файла версии. Загрузчик должен иметь рабочий DNS и выход до первоначальной загрузки правил. В sing-box 1.14 изменился механизм HTTP-клиента; параметры `http_client`/`download_detour` подбираются по версии, а не копируются между версиями вслепую. Для первого испытания используйте local или встроенные условия, чтобы исключить зависимость от загрузки списка.

## Изолированная копия локальной конфигурации

Сохраните полную исходную конфигурацию в `.private/base.json` и запустите одну из команд:

```sh
node scripts/integrate.mjs --format xray --base .private/base.json --out .private/trial-xray.json
node scripts/integrate.mjs --format singbox --base .private/base.json --out .private/trial-singbox.json
```

Команда требует уже существующих outbounds `direct` и `proxy`. На вход нужен полный итоговый клиентский JSON, а не шаблон Remnawave без подставленного `proxy`. Она создаёт новый файл с правами владельца, отказывается от перезаписи и не активирует профиль. Исходный файл, подключения, DNS, слушатели и прочие корневые поля сохраняются.

В новой копии блок маршрутизации заменяется выборочным alpha. В Xray блок `routing` заменяется целиком; активный routing script вызывает отказ. В sing-box заменяются `route.rules` и `route.final`, остальные настройки route сохраняются. Старые rule-set сохраняются, так как DNS может ссылаться на них. Старые правила блокировки BitTorrent, системного API, локальной сети и управления DNS в новый список не переносятся автоматически. Поэтому полученную копию сначала разберите и проверьте нативным ядром; не назначайте её рабочим пользователям автоматически.

## Безопасное обновление и откат

1. Скачайте три файла и `release.json` одного тега в новый каталог.
2. Получите SHA256 самого `release.json` из доверенного проверенного коммита.
3. Выполните `node scripts/verify-release.mjs --dir PATH --manifest-sha256 SHA256`.
4. Подготовьте новый тестовый шаблон/профиль, проверьте ядром и испытайте реальные сценарии.
5. Переключите только тестовую группу. Сохраните прежний шаблон и фиксированный тег для отката.
6. После проверки обновите выбранные рабочие подписки. Программы проекта этого не делают сами.
