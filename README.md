# Liberta Routing

**Твой трафик — твоя территория.** Liberta Routing: берём сеть под контроль. Независимые правила для Xray, sing-box и Remnawave.

Первая версия — **v0.1.0-alpha**.

Alpha содержит **8 точных хостов** в двух классах. Для каждого проверены официальные источники, указаны даты добавления и проверки. Региональная доступность и полные пользовательские сценарии ещё не измерены. Набор предназначен для отдельного тестового профиля.

Это отдельный выборочный профиль рядом с рабочим Smart v5. Присланные исходники проверены: прежний реестр содержит 13 классов, 111 уникальных доменов и 45 явных direct-записей. Compatibility-сборщик сохранён с небольшой защитной правкой; повторная сборка Smart v5 совпала с исходником побайтово. Внутренние реестр, отчёты и история профилей остаются закрытыми. Подробности: [проверка регрессии](docs/LEGACY_REGRESSION.md).

## Поведение alpha

- Явно перечисленные точные хосты → `direct`.
- Остальной TCP/UDP-трафик → `proxy`.
- Поддомены не добавляются автоматически. Сервисы могут требовать дополнительные API/CDN-хосты.
- Правила по стране, геобазы, сторонние подборки, регулярные выражения и поиск по фрагменту домена отсутствуют.
- Статусы `candidate` и `disabled` не экспортируются. Суффиксные правила нельзя одобрить в alpha.

У Smart v5 также есть широкий direct по географическим базам и специальные правила. Alpha намеренно проверяется отдельно: она не является заменой всего Smart v5.

## Файлы правил

| Файл | Формат и назначение |
| --- | --- |
| [smart.xray.json](releases/v0.1.0-alpha/smart.xray.json) | Объект `routing` Xray: точные доменные правила и явный последний маршрут `proxy` |
| [smart.singbox.json](releases/v0.1.0-alpha/smart.singbox.json) | sing-box source rule-set версии 1; только условия совпадения, без outbound |
| [smart.domains.txt](releases/v0.1.0-alpha/smart.domains.txt) | По одному `full:hostname` на строку; тип совпадения сохранён |
| [release.json](releases/v0.1.0-alpha/release.json) | Контрольные суммы, размер, количество хостов и границы проверки |

JSON Xray — фрагмент `routing`, а не полная конфигурация подключения и не `geosite.dat`. Xray сам не загружает этот JSON как удалённый список. TXT использует явные типы совпадения и не является универсальным форматом импорта любого клиента.

Source rule-set sing-box содержит условия, но не выбирает outbound: в клиенте нужно привязать его к `direct` и задать `route.final: "proxy"`. Инструкции: [подключение к Remnawave и клиентам](docs/INTEGRATION.md).

Опубликованные версии подключайте по фиксированному тегу или коммиту. Не используйте движущийся `main` как автоматический канал производственных обновлений. GitHub prerelease не считается `latest`.

## Локальная проверка

Нужен Node.js 22 или 24; установка npm-зависимостей не требуется.

```sh
npm run verify
npm run verify:legacy
node build.mjs --out .local/trial-release
node compare-lists.mjs --base .private/previous-registry.json
node service-canary.mjs --out .private/canary-trial.json
```

Сборка детерминирована. `npm run check` сверяет уже сохранённую версию побайтово; сборщик отказывается перезаписывать каталог выпуска. `verify:legacy` требует закрытую исходную копию; публичный CI тестирует compatibility-сборщик на синтетических данных. `release.json` — дополнительный файл метаданных, не четвёртый формат правил.

Проверка реальными парсерами на Linux amd64:

```sh
python3 scripts/install-cores.py
PATH="$PWD/.local/bin:$PATH" npm run verify:cores
```

Версии и SHA256 исполняемых файлов закреплены в [toolchain.json](toolchain.json). Проверяются Xray и две версии sing-box. Исполняемые файлы и чужие геобазы не входят в репозиторий. Проверка парсером не доказывает работу сайта или приложения.

## Собственные данные

[registry.json](registry.json) — единственный источник правил. Хосты отобраны вручную по официальным страницам; не импортировались чужие routing-списки, подборки, исходники или сборки геоданных. Сохраняются ссылки и собственные краткие описания проверенных фактов, без копирования текста страниц.

`approved` означает «одобрено для этого alpha-профиля по проверке источника». Оно не означает «сервис проверен из России». У всех начальных записей `verification.reachability` равен `not-measured`. Процесс: [PROVENANCE.md](docs/PROVENANCE.md).

## Обновления

1. Добавить запись-кандидат и проверить официальный источник.
2. Отдельно исследовать DNS/TLS и реальные сценарии сервиса из нужных сетей.
3. Изучить diff маршрутов, одобрить точные хосты и обновить [route-lock.json](route-lock.json) с причиной.
4. Повысить версию, собрать новый каталог `releases/v...`, пройти проверки.
5. После ручной проверки запустить `Publish reviewed alpha` в GitHub Actions. Workflow проверит данные и нативные парсеры и создаст prerelease.
6. Испытать новую версию отдельным профилем, затем обновить привязку производственной подписки. Для отката вернуть прежний тег/коммит и прежний шаблон.

Canary никогда не меняет реестр. Плановая проверка имеет только `contents: read`, не создаёт PR и не публикует отчёты. Проверка источников имеет срок 90 дней: просрочка останавливает новую сборку, но не удаляет правила из ранее опубликованного выпуска.

## Публичные и закрытые данные

В публичной части находятся реестр публичных сервисов, код, документация, тесты и правила. Адреса VPN-узлов, подписки пользователей, параметры подключений, токены и инфраструктура диагностики здесь не хранятся. Локальные конфигурации и результаты canary разрешены только в `.private/`, который исключён из Git.

Перед коммитом выполняется `npm run audit:public`. Автоматический сканер дополняет ручной просмотр: он не способен распознать любой секрет или определить назначение произвольного доменного имени.
